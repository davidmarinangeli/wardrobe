# Feature 03 — Persistent background synchronization

## Scope, workflow, and ownership

The local React/Vite/Node archive remains authoritative. This feature adds a server-only persistent synchronization worker, stable checksummed snapshots, resumable uploads, reconciliation, and safe read-only status. OAuth and environment configuration never enable backup or write archive files on Google Drive. Feature 04 owns the activation matrix, explicit archive choice, and restore; feature 05 owns settings and final operational documentation.

OWNER writes this plan before code. CODER owns the new sync/snapshot modules, necessary bounded-client/auth/API integration, archive streaming hash changes, isolated tests, and this evidence record. REVIEWER independently inspects the final implementation and exercises failure cases; CODER fixes every actionable P1/P2 and REVIEWER rechecks. PUSHER stages exactly feature paths and commits locally, without pushing. All agents share this checkout and must preserve others' edits. Never read the real `.env`, modify real user data, or call real Google/AI services for tests.

## Existing seams

Reuse `googleDriveApi(...).getService()` and its exact auth-service singleton for refresh, disconnect/relink, and full target-generation fencing. `service.getTarget()` supplies `{ targetFingerprint, connectionGeneration, accountId, folderId, driveId }`; every queued job and remote mapping binds all fields, plus a sync epoch. `service.getClient(expectedTarget)` is the only authenticated bounded transport surface. Do not export raw requests or arbitrary-URL transports.

Use `buildArchiveInventory`, `validateArchive`, and `resolveArchiveFile` with the existing explicit catalogs/media allowlist. Catalog paths stay archive-relative and contain no required Drive IDs. `.google-drive` remains globally reserved and excluded from HTTP, Vite/static copies, Git, and inventories. Private connection state, queue/index, upload session URLs, snapshot staging, and lock/control records remain under the configured data root's `.google-drive`. Preserve malformed state and report it; never silently reset or leak its contents.

## Stable local snapshots and publication

Drive has no atomic multi-file transaction. Updating the last completed snapshot in place would make its old manifest invalid while transfers run. Use a managed candidate snapshot folder below the configured Drive folder, containing the same portable relative names and directories as the local archive. A root commit descriptor selects the completed snapshot; the snapshot contains its own complete inventory. Catalogs inside it require no Drive IDs, and copying that snapshot folder to a data directory remains portable. Candidate staging is temporary, not user-visible version history. Retire the previous managed snapshot only after the new commit descriptor has been read back and verified. Unknown foreign root files remain untouched.

Prepare a private durable local snapshot before remote mutation. Enumerate/hash the source, stream-copy each bounded allowlisted member into a private staging directory, verify staged size/hash, validate catalogs and referenced media, and enumerate/hash the source again. Reject/retry a changed source inventory or invalid/mixed catalog/media snapshot. Stage bytes must be immutable for the whole queued job; do not upload live source paths. Stable file bytes and inventory/reference validity must hold even when AI/web/CLI writers mutate the source. Existing per-file atomic writers remain usable; full mutation admission/drain for restore belongs to feature 04. Replace the inventory's whole-file reads with streaming hashes so large originals do not become giant buffers.

The commit descriptor is published only after all candidate members and its inventory are verified using actual Google checksums or streamed download/hash. `appProperties.wardrobeSha256` never proves byte integrity. Complete progress and `lastCompletedBackup` update only after the complete snapshot and descriptor are verified. A failed snapshot leaves the prior committed snapshot selected. Crash after descriptor publication but before local acknowledgement must reconcile the descriptor and finish local completion without another duplicate publication.

## Durable queue and reconciliation

Use one versioned restrictive atomic state record (or equivalent coordinated records) storing activation/control state, target, epoch, desired snapshot fingerprint, current committed snapshot, per-path Drive mappings, persistent operations, upload session/offset, retry state, and last complete backup. Stable operation identities include target fingerprint, full connection generation, epoch, snapshot identity, portable path, and hash. Persist identity before a create/session/mutation and acknowledgement after verification; each transition must be recoverable after restart.

Remote folders/files get ownership and operation metadata. Reconcile complete parent listings before retrying uncertain creates. Prefer persisted generated Drive IDs for create idempotence where supported, or a stable operation marker with explicit duplicate detection; never select the first duplicate name. A lost acknowledgement after folder/file creation must discover the intended existing object rather than create a duplicate. Foreign files with colliding names or ambiguous owned candidates produce an explicit safe conflict, never arbitrary deletion. Retired staging cleanup can delete only proven managed content; additions matching archive paths inside the owned snapshot follow local precedence, while unknown foreign data must not be erased.

Build a desired complete portable snapshot. Reuse verified remote bytes for unchanged members through bounded server-side copies if practical; unchanged equivalent reruns perform no content transfers or publication. Upload changed/new members, omit locally deleted members, and retire obsolete managed copies after commit. On normal enabled sync, external modifications/deletions/additions within archive paths are overwritten by the complete local snapshot. Periodically reconcile remote integrity even if the local fingerprint did not change. Remote read/list/permission/network failures are errors, never evidence of an empty archive. A 404 for a previously mapped object requires a successful complete parent listing before concluding that object was deleted. Preserve complete-pagination and incomplete-search rejection from feature 02.

Poll the allowed local inventory to discover changes from web, AI jobs, CLI and agent scripts; do not depend solely on HTTP events. Coalesce changes while a snapshot is running, then capture the newest stable snapshot. Persist retry/backoff information; transient failures survive restart and recover automatically. Permission/reconnect/ambiguous/corrupt state remain explicit. The outage notice is exactly:

> Le modifiche vengono salvate sul computer. Quando il collegamento sarà ripristinato, l’archivio locale sovrascriverà quello su Google Drive.

## Worker lifecycle and feature 04 contract

Provide a singleton server worker per archive, serialized `runOnce`/control transitions, and a cross-instance/process ownership lock for remote writers. Do not start a second independently constructed auth service. Dev/preview lifecycle starts a passive poller and closes/drains it with the server; build does not start remote work. Only a previously persisted authorized activation may resume on startup. Multiple browsers observe the same worker.

Expose internal server-only methods for reading a complete remote preview and local fingerprint, committing an authorized archive choice against those exact preview fingerprints/target, pausing and draining, resuming, disabling while retaining both copies, and invalidating/replacing the epoch after restore. Activation must require a validated decision/evidence contract intended for feature 04, with no HTTP blind enable route. A decision must be rejected when either preview or target changed; `use-local`, `equivalent`, and `initialize` must match their documented conditions. Feature 04 supplies human consent and handles `use-drive` by verified restore before activating. No OAuth callback, status read, verify, or mere folder configuration calls the activation method.

Pause/disable must stop future outbound writes and await in-flight requests; generation/epoch checks before and after every await prevent stale completions from altering a new queue, status, index, or target. Account/folder/relink changes invalidate mappings and resumable sessions. Restore invalidation clears obsolete work, retains no old remote IDs/session URLs, and leaves synchronization paused until the coordinator explicitly completes its authorized replacement. Do not reinterpret corrupt private state as disabled/empty success.

Feature 04 must stop/drain outbound work before reading its selected restore preview, block new local mutations, drain real AI/background promises and CLI writers, verify staging, reject changed preview fingerprints, use a durable replacement/rollback journal, set archive generation greater than previous-local and remote generations, seal legacy browser migration, and invalidate all mounted derived data/media caches. The feature 03 seams must support these steps; HTTP request completion alone is insufficient. Local emptiness is semantic: startup defaults such as `library=[]`, metadata, and browser-state files do not make an archive populated.

## Bounded resumable/streamed primitives

Extend the existing client only as necessary: stable create identity/ownership metadata, bounded copy, resumable initiation/query/chunk completion, and streamed hashing/download. Validate ancestor/root/current target before and after every transport, including successful and failed responses and final body consumption. Persist session URL and confirmed offset server-only before continuing. Session URLs must be exact HTTPS Google upload endpoints with a valid upload ID, never user-selectable arbitrary destinations; reject redirects and invalid Location values. Existing root/per-item/shared-drive permissions and native-document/shortcut rejection remain in force.

Chunk reads remain bounded (for example 8 MiB and a 256 KiB multiple); upload originals larger than 64 MiB without constructing their entire byte buffer. Handle `308 Resume Incomplete`, missing/validated Range, status probes using `Content-Range: bytes */<size>`, lost final acknowledgement, and expired sessions by reconcile/restart under the same operation identity. Do not assume all submitted bytes arrived. Downloads/hash consume streams with current-generation checks and a byte count/checksum verifier. Curate safe errors; session URLs/credentials/raw provider messages never enter status or logs.

Resumable details follow [Google upload guidance](https://developers.google.com/workspace/drive/api/guides/manage-uploads); stable IDs and server copies follow [files.generateIds](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/generateIds) and [files.copy](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/copy). All calls preserve the feature 02 folder boundary.

## Safe status and integration

Include `backupEnabled`, sync state, current/total files and bytes, pending changes, safe retry/error, paused state, and `lastCompletedBackup`. Counts reflect snapshot completion, not merely submitted requests. Never include private filesystem paths, queue payloads, token/session URLs, raw exceptions, or remote file IDs used solely internally. Feature 05 can render this shape. ## Decisive isolated verification

1. Upload/update/delete roundtrip, valid portable catalogs/layout, complete inventory published last, prior committed copy remains selected on intermediate failure, and an equivalent rerun has zero unnecessary content transfers.
2. Lost acknowledgements for folders/files/publication, explicit duplicate-name/ownership ambiguity, retry/restart without duplicates, cleanup preserving arbitrary foreign root/unknown files.
3. Durable queue restart/offline/backoff recovery and interrupted resumable sessions, including expired session and lost final acknowledgement; a >64 MiB original uploads through bounded chunks and streamed verification.
4. Script mutation discovery and local precedence after outage/external remote byte edit/delete/addition; appProperties hash spoofing does not bypass real checksum/hash.
5. Access/403/404/listing/incomplete-search failures never cause emptiness or destructive actions. Obsolete generation success/error, account/folder changes, restore epochs, and disconnect cannot acknowledge old work or reuse old IDs/sessions.
6. Disabled/configured/OAuth-only/status-only cases perform no Google writes. Pause/drain/disable/invalidate and concurrent run/control calls preserve one writer and safe state/status.
7. Corrupt private state is preserved. Corrupt/mixed/mutating local snapshots never publish; failure preserves last completion. Safe status exposes no secret/session/private path.
8. Focused tests, `npm test`, `npm run build`, changed module syntax, and `git diff --check`. Use only temp directories/injected remote mocks. If loopback requires sandbox escalation, use the authorized fake-only escalation rather than skipping. Avoid repeating checks after they pass unless changes/failures justify them.

## Implementation evidence and handoff

### Implemented seams

- `scripts/google-drive-sync.mjs` exports `createGoogleDriveSyncWorker`, `getGoogleDriveSyncWorker`, and `GoogleDriveSyncError`. The Vite integration reuses the exact auth service from `googleDriveApi(...).getService()` and exposes the server-only worker via `getSyncWorker()` for feature 04. Worker methods are `start()`, `stop()`, `runOnce()`, and side-effect-free curated `getStatus()`/`getSafeStatus()` aliases. `preview()` returns a server-only evidence ID, target, local fingerprint/inventory/private stage path, and remote validation result/maps/private stage path; its remote IDs and paths must never be sent to the browser. `cancelPreview(evidenceId)`/`discardPreview(evidenceId)` dispose those staged copies and return a boolean. The evidence is single-use, expires in ten minutes, and the worker caps retained previews at 24. There is no HTTP activation or restore route.
- The private atomic state lives at `<dataDir>/.google-drive/sync-state.json`; control fence and cross-process writer lock are `sync-control.json` and `sync.lock`. Durable candidate bytes and downloaded preview evidence stay in private `snapshots/` and `previews/`. Invalid or oversized state is left untouched and status does not expose the private contents.
- Each completed backup is a named snapshot folder with archive-relative catalog/media paths, required nested folders, and `.wardrobe-inventory.json`. `wardrobe-archive-commit.json` selects it by portable folder name, inventory fingerprint/hash, and publication time; it contains no Drive IDs. Manual folder copies and raw-root inventory layouts are read by names and actual checksums without relying on appProperties. App properties only help manage worker-owned artifacts.
- A frozen candidate inventory/stage is persisted before remote writes. Unchanged files are verified then copied server-side where possible; new/changed files use resumable 8 MiB chunks. Each candidate has a unique persisted snapshot name, and create/copy/upload operation identities include it so a same-fingerprint repair does not reuse retired IDs. Cached candidate folders are revalidated on restart; confirmed missing folders get fresh identities and invalidate dependent file/session mappings while keeping frozen bytes. The complete candidate and inventory are verified again before pointer publication; the previous completed snapshot remains selected until the new pointer is read back. Durable cleanup records bind the retiring copy to the exact new snapshot ID/name and descriptor hash. Before deleting, the worker re-reads the root pointer and confirms it still selects that identity. The same complete-selection guard protects orphan cleanup: unreadable/invalid pointer state permits no deletion; exact adoption by both the validated root selection and `lastCompleted` drops stale cleanup bookkeeping without deleting the selected object; a selected but unadopted object remains protected. An unchanged fingerprint alone is never cleanup authority. Unknown, modified, or unverifiable members remain as residue and produce `cleanup_pending`; later backups continue.
- Private snapshot stages are pruned only under the writer lock and only after the state record parses and validates. The durable candidate and stages referenced by valid controls are retained; malformed state and its evidence are never swept. Preview evidence has a ten-minute TTL and a 24-entry cap; explicit `cancelPreview`/`discardPreview` removes its staged copies.
- The worker serializes its own remote writes and control transitions under one in-process queue plus a cross-process writer lock, and checks the full target plus epoch after awaited client operations. This does not admit or drain every web, AI, and CLI local writer; Feature 04 owns that archive-wide admission/drain barrier. Feature 04's `use-drive` bridge is `authorizeRestore({ evidenceId, source: "feature04", confirmed: true, choice: "use-drive" })`, which revalidates the one-use preview/target and returns `{ restoreAuthorizationId, target }`. Then call `invalidateAfterRestore({ target, restoreAuthorizationId })`, perform the journaled restore/seal, and call `completeRestore({ target, epoch, restoreAuthorizationId })`. Invalidation returns `{ epoch, target, restoreAuthorizationId }`, preserves the previous enabled/disabled mode, and leaves writes paused. Completion re-reads the same remote descriptor and validates all archived payload bytes, allowing only a strictly newer `archiveGeneration` than both previous-local and selected-remote metadata. `archive-metadata.json` may change only that generation field. `browser-state.json` must use the same new generation, set `migrationSealed: true`, set `migratedFields` to the full known list (`itemEdits`, `deletedIds`, `colorProfile`, `declutterKeptIds`, `dismissedNudges`, `modelTier`, `onboardingDismissed`, `wornToday`), and advance `revision` no less than the remote value; every other browser/user field and every other payload file stays byte-identical. Only a valid, unexpired capability produced by explicit `use-drive` consent can complete and enable the restored archive. `use-local`, `equivalent`, and `initialize` continue through `commitArchiveChoice` and its exact preview evidence. The 8 MiB resumable chunk is bounded and a multiple of 256 KiB; source files, inventory and validation hashes are streamed, so originals above 64 MiB never need a whole-file upload buffer. `GET /api/google-drive/status` merges only the curated sync shape; dev/preview starts the passive poller and server close drains it. Build does not start the worker.
- Archive inventory and validation now hash files by stream. The bounded Drive client adds generated IDs, server-side `copyFile`, stream hash/download, resumable create/update/query/chunk methods, strict Google upload URL validation, ancestry/capability checks on session transport, and streamed generation fences. Authenticated requests reject redirects; the upload response path accepts Drive's blank 200 session-init and 308 responses without assuming `response.ok`. The portable path app property stores a SHA-256 marker rather than the raw path, keeping Google Drive's combined UTF-8 key/value byte limit for long local archive names.
- Verified implementation bounds: stream hash/download is capped at 2 GiB per file; non-resumable content at 64 MiB; resumable chunks at 8 MiB (a 256 KiB multiple); validated ancestry at 32 levels; a complete listing at 100 pages/50,000 entries; remote inventory JSON at 16 MiB and commit descriptor JSON at 1 MiB; private sync state at 64 MiB. Polling runs every 15 seconds, full remote integrity verification every 5 minutes, and retry delay is capped at 5 minutes. Each Drive `appProperties` key/value pair is checked against Google's 124-byte combined UTF-8 limit before transport.

### Restore coordinator recovery boundary

Preview and restore capabilities are process-local, expire after ten minutes, and refer to private preview staging. A persisted `restoreAuthorization` fence does not reconstruct the in-memory capability after a restart. Feature 04 must integrate its durable restore journal and startup recovery before passive preview cleanup or outbound work resumes: interrupted restores require verified rollback or a journal-backed reauthorization/recovery extension, never blind completion or `resume()` of partially replaced data. Feature 04 should keep journal-owned staging distinct from disposable preview/candidate paths or explicitly register those references with cleanup. The current worker supplies the paused epoch/control fence and checked completion contract; the archive-wide writer barrier and restart-safe restore transaction remain Feature 04's responsibility.
