## Existing integration and archive boundary

Vite registers backend plugins through `configResolved`, `configureServer`, and `configurePreviewServer`. The data root is `path.resolve(config.root, WARDROBE_DATA_DIR || "data")`. Feature 01 exports `ARCHIVE_CATALOGS`, `ARCHIVE_MEDIA_ROOTS`, `buildArchiveInventory`, `validateArchive`, and `resolveArchiveFile` from `scripts/archive-store.mjs`. Its explicit allowlist already excludes unknown/hidden OAuth and connection control files. Catalogs keep portable relative paths and must never require Drive IDs.

Use a dedicated private control directory `<dataDir>/.google-drive/`, containing `connection.json`; future queue/index/activation state may share it. Its location is fixed relative to the data root so there is no additional arbitrary secret-file environment path. It is outside all archive allowlists, ignored by Git even for a custom data directory under the repository, and protected from Vite dev/preview static serving. File permissions alone are insufficient because Vite runs as the same user.

Do not create a private directory or token file on startup when Drive is unconfigured. Missing configuration, invalid configuration, damaged private state, permission failure, and Google outages must produce a safe Drive status while the rest of Wardrobe starts and operates locally. Preserve damaged files rather than resetting them to an empty connection. Do not enumerate/read the real archive during tests.

## Configuration and scope decision

Add these backend-only `.env.example` entries:

| Variable | Meaning |
| --- | --- |
| `GOOGLE_DRIVE_CLIENT_ID` | Google Cloud OAuth web client ID |
| `GOOGLE_DRIVE_CLIENT_SECRET` | OAuth client secret; never returned by API |
| `GOOGLE_DRIVE_REDIRECT_URI` | Exact registered callback, normally `http://localhost:5173/api/google-drive/oauth/callback` |
| `GOOGLE_DRIVE_FOLDER_ID` | Existing destination folder ID, not a Drive URL |

All four are optional as a group for local-only operation. Partial settings report `configuration_incomplete`; malformed folder IDs or callback URLs report `configuration_invalid`. Reject callback URL credentials, query/fragment components, unexpected callback paths, and non-HTTPS URLs except localhost/loopback HTTP. Config snapshots and tests may inject environment values without modifying `.env`.

Request `https://www.googleapis.com/auth/drive` plus `openid email profile` through authorization code flow with offline access. `drive.file` only covers files created/opened/shared with the application, including Picker grants; it cannot reliably read/write an arbitrary preconfigured folder and an archive copied there manually from another installation. Full `drive` scope is therefore necessary for the approved folder-ID workflow, while every implemented file operation is bounded locally to that root. This is a restricted Google scope: users configure their own OAuth project/consent screen; public distribution may require Google verification. The scope choice follows [Google's Drive authorization guide](https://developers.google.com/workspace/drive/api/guides/api-specific-auth). No Picker or second Google account is introduced.

Use built-in Node crypto, fs, and fetch rather than adding a dependency solely for these REST calls. Google endpoints are constants, never browser-supplied URLs. Inject transport, clock, and randomness for deterministic tests. Use explicit bounded network timeouts and sanitized structured errors; do not log request bodies, authorization headers, callback query strings, upstream messages, secrets, or tokens.

## OAuth, persistence, and connection lifecycle

Create `scripts/google-drive-auth.mjs` (configuration + connection service) and `scripts/google-drive-api.mjs` (Vite adapter), with coherent exports documented after implementation. The service constructor receives `{ root, env, fetchImpl, now }`; it must not eagerly contact Google. Suggested factory: `createGoogleDriveService(options)`.

Authorization starts only from an explicit same-origin POST. Generate separate unpredictable state and browser nonce, persist neither in catalog state, and retain pending attempts in an expiring in-memory bounded map. Bind the state to a `HttpOnly; SameSite=Lax; Path=/api/google-drive/` cookie with ten-minute maximum age; add `Secure` for HTTPS. Store a digest of the browser nonce, a config fingerprint, expiry, and a PKCE verifier in the pending attempt. Include PKCE S256, `access_type=offline`, and a consent/account-choice prompt to obtain a refresh token and let the user choose their habitual account. Browser receives only the Google authorization URL and transient cookie, never client secret or token. Callback consumes the attempt once before exchanging its code. Check state, cookie binding, expiry, and config snapshot even for denial. Missing/mismatched cookie, stale/replayed state, denial, missing code, and partial consent are explicit errors; no token exchange occurs for rejected callbacks.

Exchange the code server-side with the exact callback and verifier. Require a usable access token, expiry, offline refresh token, and adequate granted scope. Fetch account identity via Google's authenticated userinfo endpoint (`sub`, email, display name), then verify the configured folder with this candidate token. Only after all validation succeeds may a restrictive atomic write replace `connection.json`. A failed callback must preserve a previously valid connection and its token file. Never reuse a refresh token from an unverified different candidate/account/config. If same-account token reuse is necessary for a provider response omitting a refresh token, prove candidate identity and matching auth configuration before reuse; preferably request consent and fail clearly when offline permission was not supplied.

Private state schema contains version, configuration fingerprint, connection generation, account metadata, verified folder metadata, deterministic target fingerprint, access/refresh token, expiry, scopes, connected/verified timestamps, and reconnect-required state if needed. Validate the whole schema on read. Fingerprint OAuth client and callback/config identity so a changed client/folder cannot reuse previous tokens or remote IDs. Derive the transfer target fingerprint from OAuth client identity + Google account `sub` + configured root folder ID + shared-drive ID where applicable. Generate a new connection generation for each accepted connection; old handles must fail after disconnect/relink, even when the target fingerprint is unchanged. Token refresh keeps the same target/generation.

Create private directories with mode 0700 and files with mode 0600; restrictive permissions also apply after atomic replacement and to existing files. Reject symbolic links/nonregular files instead of following them. Preserve a malformed token file and expose `private_state_invalid`. Atomic persistence failure must not switch the in-memory connection or lose an existing on-disk connection. Serialize refresh/persistence/disconnect/relink operations and guard completion by connection generation, so an old in-flight refresh cannot resurrect a disconnected or replaced connection.

Access tokens refresh proactively near expiry. Concurrent users share a single refresh. When an authenticated Google request returns 401, force one refresh and retry once; one temporary 401 is not revocation. `invalid_grant` during refresh marks reconnect required without deleting evidence; timeouts, transport failure, 429, and 5xx remain retryable unavailable states and preserve refresh credentials. A failed code exchange must not revoke an older accepted connection. A second 401 is authentication unavailable/reconnect-needed as appropriate, with an explicit code. Successful later verification/request can clear transient errors. Ordinary `403` is permission failure, never successful emptiness; Google's `403` reasons `rateLimitExceeded` and `userRateLimitExceeded` are retryable limits, as documented in [Drive error handling](https://developers.google.com/workspace/drive/api/guides/handle-errors). Disconnect clears the local connection only through an explicit same-origin action; optionally revoke the token server-side, but network revocation failure must be explicit and must never leak credentials. Disconnect does not touch local or remote archive files.

## Safe HTTP and service contract

Mount the private-file guard before other middleware in dev and preview. Add Vite `server.fs.deny` entries while preserving its default secret patterns. Block the private directory through root-relative paths, `/@fs/`, encoded paths, query variants, public/build paths, and existing symlink aliases resolved to its real path; cover IPX's public/build file lookup as relevant. Reject private paths under `publicDir` or `build.outDir` as Drive configuration errors so a build cannot copy them into static output. Never import private state into client modules. HTTP regression fixtures must prove a known marker cannot be obtained through these routes in real Vite dev and preview servers. Archive enumeration and `resolveArchiveFile` must exclude/reject private control state too.

Proposed endpoints:

| Endpoint | Behavior |
| --- | --- |
| `GET /api/google-drive/status` | Passive, safe status snapshot; no implicit authorization/sync/remote mutation |
| `POST /api/google-drive/oauth/start` | Same-origin explicit start; returns `{ authorizationUrl }`, sets nonce cookie |
| `GET /api/google-drive/oauth/callback` | One-time state/code handler; clears nonce cookie and immediately redirects to clean fixed app URL with only a safe result code |
| `POST /api/google-drive/verify` | Same-origin explicit account/folder recheck; returns safe status |
| `POST /api/google-drive/disconnect` | Same-origin removal of the connection; no archive mutation |

Reject unsupported methods and cross-site mutation requests. Require the request Origin and configured callback origin to agree for control POSTs; do not use an arbitrary client return URL. Callback responses use `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and a clean fixed redirect without auth code, state, token, upstream text, or secret. API errors are `{ error: { code, message, retryable } }` with curated human-safe messages, never raw exception detail. Tests may inspect injected server-only errors internally.

Safe status fields include `configured`, `state`, `connected`, `reconnectRequired`, `account: { id, email, name } | null`, `folder: { id, name, driveId, readable, writable } | null`, `targetFingerprint`, `connectionGeneration`, `connectedAt`, `verifiedAt`, and safe `error`. States distinguish `unconfigured`, `configuration_incomplete`, `configuration_invalid`, `disconnected`, `connected`, `unavailable`, `reconnect_required`, `folder_access_denied`, `private_state_invalid`, and `target_changed`. `backupEnabled` remains false for this feature; an OAuth connection must not mean active backup. Do not include token presence/values, private paths, client secret, authorization code, or pending state in this shape.

The service exposes `getStatus()`, OAuth start/callback helpers, `verifyConnection()`, `disconnect()`, `getTarget()` and `getClient(expectedTarget)`; names may be refined but the final handoff documents exact exports/signatures. `getTarget()` returns a verified immutable backend target descriptor. `getClient` checks expected fingerprint/generation and refuses mismatched/stale targets; future queues store that association. No generic raw unbounded Drive request method is exported.

## Bounded Drive primitives

Create `scripts/google-drive-client.mjs` with `createBoundedDriveClient({ folderId, request, assertCurrentTarget })`. All operations check the current target and fetch fresh metadata rather than trusting cached parents. Allow only valid opaque IDs. Root folder must be an existing untrashed real folder, not a shortcut, with `canListChildren`, `canAddChildren`, and suitable editing capability. Confirm read access with a complete children listing without creating test files. Per-item read/update/delete operations check `canDownload`, `canModifyContent`/`canEdit`, and `canDelete` as relevant; root capability cannot guarantee every descendant's permission.

Expose bounded methods for `verifyRoot`, `getMetadata`, `listChildren`, `readFile`, `createFolder`, `createFile` (multipart bytes), `updateFile` (metadata/media), and `deleteFile`. Exclude root itself from mutation/delete. Parent IDs default to configured root and otherwise require validated folder ancestry. Fetch parents recursively to prove every descendant reaches root; reject missing/ambiguous parents, cycles, excessive depth, foreign shared-drive IDs, shortcuts, trash, Google-native document content, and malformed metadata. Do not follow shortcuts even when their target appears in-root. Never let caller metadata set/alter parents or IDs, trash the root, or select a new target. Mutation methods use whitelisted metadata fields and fixed upload endpoints. Ancestry verification necessarily reads only metadata needed to reject an outside ID; no content or mutation request may be sent before successful validation.

`listChildren` uses a query scoped to a verified parent (`'<id>' in parents and trashed = false`), escaped values, explicit fields, `spaces=drive`, `supportsAllDrives=true`, and an appropriate `corpora=user` or shared-drive corpus. Follow all `nextPageToken` values, including empty intermediate pages. Reject repeated/malformed page tokens, malformed `files`, duplicate IDs, unknown/shortcut entries, children whose returned parent disagrees with the query, permission failures, and `incompleteSearch=true`. A failed page throws; it must not return the earlier pages as a complete result. Preserve duplicate names as separate entries (or throw an explicit ambiguity from a unique-name helper); never silently select the first and never represent an error as `[]`.

Metadata includes parents, capabilities, shared-drive ID, size, MIME, modified time, version, `md5Checksum`, `sha256Checksum`, and appProperties. Use Drive's actual byte checksum when available; application-provided hashes in appProperties are metadata and cannot prove unchanged remote content. Feature 03 owns portable-path mapping, complete manifest validation, duplicate reconciliation, retry/idempotence, persistent queue, transfer restart recovery, and resumable upload sessions. This feature provides working small-file multipart/create/update/read/delete primitives; no automatic background worker starts here. Large-file resume logic may be added in feature 03, with the same parent/target validation.

Drive list semantics and byte checksum behavior follow [files.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list), [File metadata](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), and [upload guidance](https://developers.google.com/workspace/drive/api/guides/manage-uploads). OAuth state/offline refresh follows [web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server) and [Google's best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices). Vite's deny list alone excludes neither public files nor every alternate plugin path, hence the early middleware guard; see [Vite server options](https://vite.dev/config/server-options#server-fs-deny).

## Implementation evidence and handoff

### Implemented backend contracts

`scripts/google-drive-auth.mjs` exports `createGoogleDriveService({ root = process.cwd(), env = process.env, fetchImpl = globalThis.fetch, now = Date.now, randomBytes, publicDir?, buildOutDir?, privatePlacementInvalid? })`, `GoogleDriveError`, `GOOGLE_DRIVE_REQUIRED_SCOPES`, and `GOOGLE_DRIVE_PRIVATE_DIRECTORY`. Construction performs no Google call. Its methods are async `getStatus()`, `startOAuth()`, `handleOAuthCallback({ state, code, error, nonce })`, `verifyConnection()`, `disconnect()`, `getTarget()`, and `getClient(expectedTarget)`. `startOAuth` returns a server-side nonce/cookie descriptor alongside `authorizationUrl`; the HTTP adapter returns only the URL and sets the HttpOnly nonce cookie. An accepted callback returns verified account/folder/target to the server adapter, which redirects to the fixed application root with only a safe `googleDrive` result code.

The immutable target descriptor is `{ targetFingerprint, connectionGeneration, accountId, folderId, driveId }`. Every field must agree with the current private record before a client is issued. The deterministic fingerprint binds OAuth client ID, Google account subject, folder ID, and shared-drive ID; each accepted connection gets a new UUID generation. Private `connection.json` version 1 additionally stores `configFingerprint`, account `{ id, email, name }`, folder `{ id, name, driveId, readable, writable }`, `accessToken`, `refreshToken`, `expiresAt` in milliseconds, granted `scopes`, ISO `connectedAt`/`verifiedAt`, and `reconnectRequired`. The config fingerprint also binds the secret and callback so configuration changes cannot reuse prior credentials. These are control records, never archive members or required catalog references.

`scripts/google-drive-client.mjs` exports `createBoundedDriveClient({ folderId, request, assertCurrentTarget, expectedDriveId? })` and `GoogleDriveClientError`. The service always supplies the saved target's `expectedDriveId` (including null for My Drive); fresh root metadata must agree before content access or mutation. The server-only `request` transport accepts `{ method, url, query, headers, body, responseType }` and returns `{ data }`, `{ bytes }`, or an empty success for `responseType: "none"`. The issued client exposes async `verifyRoot()`, `getMetadata(id)`, `listChildren(parentId = folderId)`, `readFile(fileId)`, `createFolder({ name, parentId = folderId })`, `createFile({ name, mimeType, bytes, parentId = folderId, appProperties })`, `updateFile({ fileId, name?, mimeType?, bytes?, appProperties? })`, and `deleteFile(fileId)`. `verifyRoot` returns a safe folder summary with `childCount`; list/get return verified Drive metadata including actual `sha256Checksum` where supplied by Google; read returns a Buffer. Duplicate names remain independent entries. `appProperties` accepts only `wardrobeSha256`, `wardrobePath`, and `wardrobeVersion`; feature 03 must not use application metadata as proof of remote byte integrity.

`scripts/google-drive-api.mjs` exports `googleDriveApi({ service?, env?, fetchImpl?, now?, randomBytes? })` and `createPrivateFileGuard({ root, privateDir, publicDir?, buildDir? })`. Vite registers the plugin before all other middleware. `googleDriveApi` accepts an injected matching-root service or exposes `.getService()` after configuration. Feature 03 must reuse this same instance for its worker so authorization, refresh deduplication, disconnect/relink, and generation checks share a lifecycle. A second independently constructed service is not a substitute for this seam. Mock Google through `fetchImpl` at the service/plugin; unit client tests can inject the bounded request transport directly.

`scripts/google-drive-private-path.mjs` exports the shared `hasGoogleDrivePrivatePathComponent(path)` predicate. `.google-drive` is reserved, case-insensitively, in every lexical or real filesystem path, including previous data roots. Auth static-placement checks, dev/preview middleware, and pre-copy build auditing use this same predicate. The audit validates public/build roots and resolved ancestors, then every visited directory/file and transitive symlink target before Vite copies anything. This protects retained old credentials as well as the currently configured connection; public directory cycles fail explicitly.

The HTTP routes implemented are the five routes in the endpoint table above. Status includes safe account/folder/fingerprint/generation/time fields and `lastAuthError` for a rejected candidate without displacing an existing valid connection. `backupEnabled` is always false in this feature. Network and quota errors preserve the saved connection and report `unavailable`; refresh `invalid_grant` persists reconnect-required state. Disconnect removes the local connection and invalidates pending attempts/handles; it does not revoke the entire Google project grant remotely or mutate either archive.

### Boundaries for subsequent features

- Feature 03 owns the persistent queue/index, path-to-ID mapping, idempotent retry/reconciliation, complete manifest integrity, restart recovery, and upload resume. Current multipart and in-memory download primitives cap a single file at 64 MiB, ancestry at 32 levels, and listings at 100 pages/50,000 files; exceeding a bound is an explicit error, not a truncated success. Add streaming/resumable primitives under the same target/ancestry boundary for larger originals. Obtain a current target, store it with queue/index state, and reject obsolete fingerprint/generation before work. Client metadata's byte checksums may support transfer verification; otherwise download and hash actual bytes. No worker currently starts automatically.
- Feature 04 owns storage activation, all archive-choice confirmations, complete verified staged restore/rollback, maintenance/mutation admission, process draining, generation sealing, and invalidation of previous queue work. OAuth success supplies only a verified destination. It must not upload a populated local archive or overwrite an existing remote archive before feature 04's matrix decision.
- Feature 05 owns settings UI and operational/configuration documentation. Use safe status and explicit same-origin POSTs; start requests need a JSON object body, and OAuth must open in a full browser. Return URL and consent-result codes carry no secret. No backup UI is added here.
