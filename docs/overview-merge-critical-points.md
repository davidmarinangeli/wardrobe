# Overview merge — critical points

## Feature 01

- Naming: the imported `blockedCoverages` must not be shadowed by the old local const of the same name. Using `blocked` as the new local would also clash with the per-item `const blocked` in the `OutfitBuilder` render loop (`src/outfits.jsx`). The local is `coverageBlocks`.
- The old `useMemo` depended on `selectedItems`, which is rebuilt with `.filter().map()` on every render, so it never cached anything. Removing it does not change performance. Don't add a memo that misleads the same way.
- Index entries hold raw tags only (`entry.item.tags`); no normalised tag field exists (`buildOverviewIndex` only folds tags into `searchText` through `allText` and `normalizeOverviewText`). `filterByTags` reads `entry.item?.tags` with an Array guard, because some items have no `tags` array.
- The key `filterByTags` uses (`tagKey`: trim + `toLocaleLowerCase("en")`) must stay the same as `overviewSuggestions`' key. Otherwise feature 02's chip counts will disagree with the filtered grid. `normalizeOverviewText` is deliberately not used: it folds plurals and punctuation, so it would merge chips that are counted separately (e.g. "t-shirt" and "t shirt").
- `tagKey` is a third copy of the trim + lowercase expression, next to `overviewSuggestions` and `commonOverviewTags`. Left as is to keep the diff small; `overviewSuggestions` is out of scope for feature 01.
- Keep the `GARMENT_PART_MAP` import in `src/outfits.jsx`: `SuggestionNudges` still uses it. Keep the `useMemo` import too (`itemsByCategory`, `dismissed`, `itemMap`).
- `isPieceBlocked` deliberately knows nothing about selection. Every caller, now `OutfitBuilder` and in feature 02 the picker, must keep the `!selected.has(id) &&` guard, or a selected piece would grey itself out.
- Behaviour differs from today in one invisible way: an unknown part no longer adds `undefined` to the coverage set. Nothing reads that value, because only `full`, `upper` and `lower` are ever checked; the test states the no-contribution rule explicitly.
- Two full pieces (dress plus jumpsuit) stay allowed together: a full piece blocks only `upper` and `lower`. That is today's behaviour and the test comments it so feature 02 doesn't "fix" it by accident.
- The blocked title text is wrong in one direction today: with a top or bottom selected, a dress reads "<name> — a full-length piece already covers this". Feature 01 keeps the text unchanged; feature 02 is the place for a coverage-aware message (for example a small `blockedReason(item, blocked)` in `outfit-rules.mjs`).
- `shared/outfit-index.mjs` already exists (it holds the outfit counts index). Don't confuse it with the new `shared/outfit-rules.mjs`.
- `node --test test/` (the directory form) fails on this Node; use `npm test` or the `test/*.test.mjs` glob.

## Feature 02

- ViewerPanel has **no** Escape handling, even though the spec says Escape comes from it. Only `useViewerKeyboard` binds Escape, and it calls `onClose` directly, which would skip the confirm. The picker owns its Escape listener: on `window`, in the capture phase, with `stopImmediatePropagation`, so in feature 03 the cheat editor's document-capture Escape handler (`src/cheat-sheets.jsx` ~L519) doesn't also fire. Side effect: Escape inside the search field no longer clears it natively; Escape always means close (or Keep while the confirm is open).
- Feature 03 focus-trap conflict: two ViewerPanels with `focusTrap` each add a document Tab listener, and the editor's listener pulls focus back into its own dialog. The editor must pass `focusTrap={!pickerOpen}` while it stacks the picker.
- There is no exposed ViewerPanel dismiss, so a picker closed by Escape, Discard or a successful confirm unmounts at once with no exit animation. Only the X and overlay clicks animate (through `useDismiss`). This matches `useViewerKeyboard`'s "instant" convention; motion is an open refinement point. Don't route the X through anything other than `onRequestClose`: ViewerPanel already asks permission and then dismisses.
- Spec conflict: "Confirm disabled below `minPieces`" vs the acceptance check "Save without pieces → same message". Resolved with `minPieces={0}` for outfits; the component default stays 1 for cheat sheets (feature 03).
- On a phone the Name field and error live in the collapsed tray, so a failed Save would show an invisible error. The picker opens the tray whenever `onConfirm` rejects, which is why `OutfitPicker` rejects on validation errors instead of returning quietly. The picker never closes itself on confirm; the caller unmounts it.
- "Edit → Save → viewer shows new pieces" needed `closeBuilder` to reopen the viewer for `builderOutfit.id` (before, an edit save closed back to the grid). Save and cancel both land on the viewer, like "back". `closeBuilder` reads `builderOutfit` from the closure that `saveOutfit` captured, which is the same outfit.
- Pre-existing bug fixed: `builderOutfit` survived App resetting `showOutfitBuilder` (archive generation change), so the next Add outfit would open as an edit. An effect now clears it when `showBuilder` turns false. It doesn't race `openEditOutfit`: both updates land in one commit with `showBuilder` true.
- The picker snapshots `initialSelection` and its baseline at mount. Later prop changes are ignored on purpose: Outfits' 1.5s polling replaces outfit objects, and re-seeding would wipe the user's selection.
- The `!selected.has(id) &&` guard stays next to `isPieceBlocked` in the picker, or selected pieces would grey themselves out. `blockedReason` (`shared/outfit-rules.mjs`) fixes the wrong-direction title feature 01 deferred: with a top picked, a dress now reads "a top or bottom is already picked".
- `overviewSuggestions` counts tag occurrences, not unique items, so an item tagged `['Linen','linen']` adds 2 to the chip and a chip count can exceed what the filter shows. Minor; don't "fix" `filterByTags` to match. With a real wardrobe the tag row is long (73 chips locally) — one scrolling row as the spec asks, but a candidate for a cap or "more" later.
- `mobile-chrome.css` forces `.viewer-overlay .viewer` to a 92dvh max-height, `!important` top radii and `touch-action: pan-y`, and `align-items: flex-end` on the overlay. The picker uses two-class selectors (0,4,0) on overlay, entry and panel, sets `max-height` as well as `height`, `touch-action: auto` (so the chip rows scroll sideways) and `border-radius: 0 !important`.
- `ConfirmDialog` (`src/components/ConfirmDialog.jsx` + `confirm-dialog.css`) copies the `.cheat-confirm*` styles under generic names rather than depending on cheat-sheets.css. Its layer z-index 10 must stay above ViewerPanel's X (z 8). It renders inside ViewerPanel's children, next to the `inert` picker body, so the focus trap (which skips `[inert]`/`[hidden]`) cycles only Keep and Discard; `closeDisabled` stops the X and the overlay meanwhile. The cheat editor's two dialogs could adopt it later (feature 03/05 candidate).
- Dead after this feature, for feature 05: `.outfit-builder*`, `.outfit-category*`, `.outfit-piece*`, `.builder-piece-option`, `.builder-variant-picker*` in `src/outfits.css` (copied into piece-picker.css rather than reused), and the `OUTFIT_CATEGORIES` export in `src/categories.js`. `OutfitStack`'s doc comment still mentions "the outfit builder". `.outfit-error` (uppercase, large top margin) still styles the error in the picker footer; worth a look in feature 05.
- `OutfitPicker` re-appends the hidden pieces (itemIds not in the active `items`, from `migrateOutfit`) on every save. Without that, `normalizeOutfit` sees a changed lineup and wipes `modeledImage`, `modeledStatus`, `modeledError`, `modeledTier`, `description` and `tags` (`scripts/outfits-api.mjs` ~L46-58). Don't move this into the generic picker: `normalizePieceSelection` must keep dropping unknown ids so the count and preview stay accurate. `hasChanges` ignores hidden pieces and name edits; the confirm covers the visible selection only, as the spec says.
- Hard-deleted pieces: `DELETE /api/import/wardrobe/:id` doesn't clean up outfits, so saving such an outfit still fails with "Unknown wardrobe item". Same for a legacy `itemIds`-only outfit with a retired piece (its variantId resolves to null against active items). An outfit whose pieces are all retired shows "Pick at least one piece." (the old builder's check also ran on active items only). All parity with `OutfitBuilder`, not regressions.
- Server cap: `outfits-api.mjs` runs `value.pieces.slice(0, 12)`. The picker has no cap, so a 13th piece is dropped silently, and because hidden pieces are appended after the visible ones, they are the ones cut first — the lineup then changes and the modeled photo is wiped. `OutfitBuilder` had the same silent truncation; no cap built now.
- `normalizePieceSelection` replaces a stored variantId that no longer exists on the item with the default variant. Before, such a save failed with "Unknown variant …". Now a rename-only save succeeds, the lineup key changes, and `normalizeOutfit` wipes the photo, description and tags. Defensible (the photo came from a variant that's gone), but `hasChanges` is false so no confirm fires.
- Initial and fallback focus: the X on a phone (no keyboard pop-up, `useViewerKeyboard`'s convention), search on desktop. Never left on the background trigger. Keep returns focus to the element that asked to close if it's still connected and inside `.piece-picker-panel`, otherwise to that default.
- Disabled **Add outfit**: `title` never reaches touch users, so when blocked the trigger's `aria-label` also carries the hint ("Add outfit, Add pieces to your wardrobe first"). Setup and import-progress states keep the trigger enabled. Suggest outfit still has no hint.
- `OutfitPicker` renders for a new outfit only when `items.length > 0`, but always for an edit: Edit is reachable from an outfit's viewer even with no active pieces, and rendering nothing there left `showBuilder` stuck true with no way to close it (review fix). The edit then shows the empty state and can be closed.
- The global Drive status toast sits above the picker's header (its z-index is higher than the overlay's). Pre-existing for every panel; noticed in the browser pass.
- Browser pass done here: desktop and 390px — search, category, two tag chips (AND), empty state + Clear filters keeping the selection, Save without a name (message, picker stays open, phone tray expands), Escape with changes → confirm → Keep/Discard, Escape without changes closes, phone opens with focus on the X, Edit preselects and Escape returns to the viewer. Not exercised: blocking (no dress in the local wardrobe; unit-tested), variant thumbnails (no multi-variant piece), and any actual save (to leave the local data untouched), including the retired-piece rename case.

## Feature 03

- Name clash: `import { PiecePicker } from "./components/PiecePicker.jsx"` collides with the old local `const PiecePicker = forwardRef(...)` in `src/cheat-sheets.jsx`. The local one was deleted in the same change. After that, `forwardRef`, `ArrowLeft`, `CATEGORY_LABEL`, `WARDROBE_TYPES`, `buildOverviewIndex`, `filterByPart` and `filterOverviewIndex` were unused and are removed. `Check`, `Plus`, `variantImage` and `initialVariantForPiece` are still used.
- Focus trap: two ViewerPanels with `focusTrap` each add a `document` Tab listener, and the editor's listener would pull Tab back into the inert editor. The editor passes `focusTrap={!fullscreenOpen && !piecePickerOpen}`. Side effect: turning the trap off runs ViewerPanel's cleanup, which queues a rAF to refocus the editor's mount-time `previousFocus` (the pencil, Overview's trigger, or `<body>`). The picker's own `focusDefault` rAF is queued later in the same commit and wins, so the background element holds focus for one frame. The fullscreen viewer relies on the same ordering. Don't reorder these frames. A comment on the prop says so.
- Lost return target: when the picker closes, the editor's trap re-arms with `previousFocus` = `<body>`, because the picker's buttons were already removed from the DOM. The editor's ViewerPanel restore is therefore useless on close. `closeEditor`/`saved` go through `CheatSheetsArea`'s double-rAF `restoreEditorFocus` (`editorReturnFocus` → `.cheat-new-button`), so keep `editorReturnFocus.current = trigger` in `confirmNewSheet`.
- Create-confirm focus race: the create picker unmounts in the commit that mounts the editor. The picker's ViewerPanel cleanup queues a rAF that refocuses its `previousFocus`, the "+ Cheat sheet" button behind the editor. The editor's title focus moved from a synchronous effect to a cancellable rAF, which React queues after that one because passive unmount effects run before mount effects. Without this change, focus sits on a background button while the editor modal is open. StrictMode is on, so the effect cancels the frame on cleanup.
- Safari doesn't focus buttons on click. Both triggers (+ Cheat sheet and Edit pieces) call `event.currentTarget.focus()` before opening the picker, so ViewerPanel captures the trigger as `previousFocus`. The close paths then double-rAF an explicit `focusIfVisible` back to the trigger, after ViewerPanel's single-rAF restore: `cancelNewSheet` through `restoreEditorFocus`, and `closePiecePicker` to Edit pieces with the title as fallback.
- Escape: the picker's window-capture listener with `stopImmediatePropagation` pre-empts the editor's document-capture handler. This only works because capture visits `window` before `document`. Don't move the editor's listener to window capture. The editor's picker-mode branch and `mode` dep are gone.
- Stacking: both overlays use the base `.viewer-overlay` z-index of 40, and neither `.cheat-editor-overlay` nor `.piece-picker-overlay` overrides it. The picker paints on top only because its portal is appended to `body` after the editor's. It is rendered as a sibling after `</ViewerPanel>` in the editor's fragment and must stay there. Verified at 390px, where the editor overlay carries an inline top/height from `visualViewport`.
- An unchanged Done must not call `setSelected`. A fresh Map gives `draftPieces` a new identity and re-runs the 180ms debounced preview render. `applyPickedPieces` compares `draftShape("", next)` with `draftShape("", draftPieces)`. `draftShape` runs `normalizeCheatSheetScale`, which throws on invalid scales, but editor scales are always valid. Verified: the pencil path, then Edit pieces, then Done with no changes leaves the sheet "Saved".
- Missing pieces (items not in the active wardrobe) are passed outside `offeredIds` (`new Set(itemsById.keys())`) and are kept in place. The picker never showed them, because `normalizePieceSelection` drops unknown ids, so dropping them would silently lose data and make a no-op Done dirty. The editor already lists them as "Missing wardrobe piece" with Remove.
- Count mismatch: the editor header counts `selected.size`, which includes missing or retired pieces. The picker counts only the pieces it can show. With a missing piece present, the two numbers differ by design.
- Stale variant: a retained piece takes the picker's variantId. If the stored variant no longer exists, the picker shows and returns the default variant, so Done repairs the piece and marks the sheet dirty. Such a sheet was already unrenderable and could not be saved. The helper keeps the piece's own variant only when the picked one is null or undefined.
- `minPieces={1}` on both pickers. The editor can hold an empty draft (per-row Remove), but it can't save one: `canSave` needs `selectedCount`, and the API rejects an empty sheet.
- `renderPreview` (the `SheetPieceTray`) goes on both pickers. Without it, PiecePicker's `hasSide` is false and the phone layout has no "N selected" tray.
- `onConfirm` handlers stay synchronous and never throw. `confirmNewSheet` unmounts the picker in the same commit that mounts the editor, and PiecePicker's `mountedRef` guards stop its post-await `setPending` from running after unmount.
- `createRequest`/`returnFocusRef` stay for now (feature 04 removes them): Overview's Create cheat sheet still depends on them, and it was verified working. Both the `createRequest` effect and the `active` effect call `setCreating(false)`, so a create picker and an editor never coexist. The early return is `!active && !entry && !creating`.
- `.cheat-new-button` keeps its class name, because `saved`/`closeEditor` use it as their focus fallback. A disabled + button simply doesn't take that fallback focus.
- CSS: the plan assumed `.secondary-button` already had disabled styling in styles.css. It doesn't: only scoped variants exist, such as `.drive-settings`. The new rule covers both `.cheat-new-button:disabled` and `.cheat-collection__empty button:disabled`.
- Disabled-hint gap: Chrome doesn't reliably show a `title` tooltip on a disabled `<button>`. With an empty wardrobe and existing sheets, the header + only carries the hint in its `title` and `aria-label`. The visible `.cheat-collection__hint` renders only in the empty-collection state. This matches Add outfit in import-flow.jsx. Accepted for now.
- Dead after this feature, for feature 05: `.cheat-picker*`, `.cheat-editor__back`, `.cheat-editor__done` (including the `.cheat-editor__done + .cheat-editor__close-spacer` rule and the hover list), and the `:not(.is-picker)` qualifiers in the 860px media block, which now always match and are harmless. `.cheat-picker__search` is still listed next to the title inputs in two selectors.
- No existing test reads cheat-sheets.jsx source or its copy. `test/cheat-sheet-pieces.test.mjs` matches the `test/*.test.mjs` glob that `npm run check` runs.
- Browser pass done here, at desktop and 390px: + → pick 3 → Next (title focused, preview renders after typing a title), scale +20% → Edit pieces (remove one, add one) → Done (scale kept, new piece at 100%, Save enabled), Edit pieces with changes → Escape → "Discard this selection?" → Discard (editor unchanged, focus on Edit pieces), Escape without changes closes only the picker, cancelling the create picker returns focus to +, Shift+Tab ×4 stays inside the picker, the pencil path → Edit pieces → unchanged Done stays "Saved", Overview Pieces → Create cheat sheet still opens the editor with the selection, and on phone the picker is topmost with the tray listing the selected thumbnails. Not exercised: the empty-wardrobe disabled state (no way to empty the local wardrobe without touching data) and any actual save.

## Feature 04

## Feature 05

- CSS order matters. `mobile-chrome.css` loads first, and `cheat-sheets.css` loads before `overview.css`, because `overview.jsx` imports `cheat-sheets.jsx` before `./overview.css`. So `.overview-panel-head*` already won every tie with the duplicated `.cheat-collection__header`, `.cheat-collection h2` and `.cheat-new-button` rules, and deleting those changes nothing. Re-check this if the import order changes.
- Keep the `cheat-new-button` class in the JSX even though none of its CSS is left. `saved`, `closeEditor` and `cancelNewSheet` query `.cheat-new-button` as their focus fallback (`cheat-sheets.jsx` ~L880, L935, L944).
- Several dead selectors shared a selector list with live ones. In `cheat-sheets.css` these were the eyebrows, the title inputs (base and 860px), `.cheat-piece-count button` (which styles Edit pieces), the empty-list rule, the hover list and the disabled rule. In `outfits.css` it was the reduced-motion block. Those lists were edited rather than deleted. The 360px `.cheat-collection__header { flex-wrap: wrap; }` stays because it has no Overview equivalent.

Some selectors were already dead at baseline `331918e` and are out of scope here: `.outfit-stack.compact`, `.mirror-trigger`, `.mobile-header`, and the orphans in `styles.css` and `import-flow.css`.

The drag handlers use `closest(".overview-drawer")`. Check it at 390px anyway: collapsed, expanded, drag up and drag down.
